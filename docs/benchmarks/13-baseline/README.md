# Benchmark 第 13 步：新基线（构建并行、warm 接收、解包系统调用、数据盘持久性、vz vmnet 网络）

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`（CI run 39701096410，commit `aa21bde`；之后的 `e9e7be7` 只给 vz 加了 macOS 26 检查、改了文档，不影响这些数字）。括号里的变化是相对[第 12 步](../12-warm/README.md)。两次不在同一批 runner 上：这一次是 ubuntu-26.04、macos-26、macos-26-intel，第 12 步还是 ubuntu-latest、macos-15。**这是后续优化的新基线**：之后每一步的报告请以本目录为 `-baseline`。

## 这一步做了什么

以下各项的结论都来自同机交替 A/B（bench 工作流的 `base` 模式，3 轮），对比的是合并前的 main：

| 分支 | 做法 | 同机 A/B 结果 |
|---|---|---|
| `perf/parallel-build` | `buildPlatform` 里 base 拉取、nix（求值加下载）、组件导入三路并发；各平台并行；共享状态加锁 | 冷构建 native 2.8 → 2.1 s，kvm 2.2–2.5 → 1.6 s；加包后重建 0.25 → 0.21 s |
| `perf/guest-disk-durability` | 数据盘不保证持久化：QEMU `cache=unsafe`，VZ 不同步，ext4 `data=writeback,nobarrier`；宿主机侧标记，没有正常关机就丢弃数据盘 | kvm 冷 warm −12%，增量 warm −10%，首次启动持平（380 MiB 脏页不再拖慢 `runc create`）；qemu 持平。不要 journal（`^has_journal`）会让 `git clone` 出错，已放弃 |
| `perf/extract-syscalls` | 解包和建 view 都改用目录 fd 的 `*at` 系统调用；root 下目录直接用最终权限创建；跳过无用的 chown/chmod；硬链接查内存表 | 系统调用 −39%（22,443 个文件：25.1 万 → 15.4 万次）；建 view −38%；qemu 增量 warm 5.5 → 3.8 s。顺带修了一个目录被符号链接替换后可以穿透的 bug |
| `perf/warm-receive` | guest 不再算 sha256（保留大小、tar 头校验和、zstd CRC）；zstd 解码放到单独的 goroutine；native 直接按路径读 tar，用 `copy_file_range` 拷数据 | native 冷 warm 约 1.1 → 0.8 s，agent 处理一个产物的 CPU 时间 −50–60%；kvm 上传 −40%；qemu 持平 |
| `fix/vz-vmnet-subnet` | vz 改用 macOS 26 的 vmnet 网络，自动挑一个不冲突的 /24，guest 用静态地址（`oar.net`）；vz 只支持 macOS 26 及以上 | 修好了 CI 上 vz 的"挂起"（见下） |

没有采用：`perf/view-reuse`（新闭包的 view 从没人用的旧 view 里搬子目录）。增量 warm 能快 10 倍以上，但"等脏页写回之后的首次启动"会慢 2–3 倍：连续 warm 多个相关闭包时，旧 view 都被拆掉，启动时只能在启动路径上重建。分支留着没删。

## vz 在 CI 上"挂起"的根因

GitHub 的 macOS runner 本身就是一台在 `192.168.64.0/24` 上的虚拟机，网关和 DNS 都是 `192.168.64.1`。VZ 的 NAT 总是给 guest 分配同一个网段，guest 的 `bridge100` 一起来，就占用了 `192.168.64.1`。之后的现象：

- 宿主机 DNS 超时（`lookup cache.nixos.org on 192.168.64.1:53: i/o timeout`），nix 求值失败；
- 上传 artifact 时报 `ENOTFOUND`；
- 偶发 `read response: EOF`；
- 跑得久的 job 最终报 "The hosted runner lost communication with the server"，日志和 artifact 都拿不到。

改用 vmnet 网络之后（这次是 `192.168.65.0/24`），3 轮 vz A/B 全部跑完，没有阶段失败，51 次 DNS 探测全部正常。改 `com.apple.vmnet.plist` 对 VZ 不起作用。bench 工作流现在每一侧开跑前、以及后台每分钟，都会记录磁盘、内存、网卡、路由和 DNS 探测（`hack/ci-resources.sh`，结果在 artifact 的 `resources.log`）。

## 已知的代价

- 增量 warm 比第 0 步基线慢（kvm 21 → 210 ms，vz 0.45 → 2.2 s，qemu 0.3 → 3.3 s），因为新闭包要建硬链接 view，这是有意保留的取舍。
- native 冷 warm 比第 0 步基线慢（1.16 → 2.26 s），原因同上。native 也不在 warm 结束时刷盘，首次启动时宿主机上还有约 1.1 GiB 待写回。
- guest 缓存遇到宿主机崩溃会丢，需要重新 warm 一遍。
- guest 不再校验 sha256：宿主机缓存盘上的位腐烂不会被发现。
- vz 依赖 Code-Hex/vz v4 的主线，还没打 tag，`go.mod` 里固定的是伪版本 `16f4ca2`。
