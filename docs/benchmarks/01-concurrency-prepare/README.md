# Benchmark 第 1 步：并发、预组合与预创建

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`；括号里的变化是相对[第 0 步基线](../00-baseline/README.md)。运行环境同基线（GitHub Actions；qemu 是 Apple Silicon runner 上的 TCG 纯软件模拟）。
> 本次测试的代码版本也包含了合入的 PR #1（内嵌 iets Nix 求值器），所以构建相关指标的变化主要来自它。

## 这一步做了什么

| 改动 | 目的 |
|---|---|
| agent 从一把全局锁改为**按容器名加锁**（外加一把读写锁，只在 StopAll 时独占） | 不同容器可以并行启动 |
| `oar warm` 时**预先组合**（生成 bundle 模板和 store 视图） | 某个组合第一次启动不再付组合的开销 |
| 新增 **`oar prepare`**：提前完成 compose、mount 和 `runc create`，进程不启动；下一次 run/reload 同一个组合时直接用它 | 切换时省掉组合和创建 |
| 修正启动探测：探测 agent 时每次尝试的超时从 3 s 降到 0.75 s，失败后 20 ms 就重试 | 不再因为一次连接挂起白等 3 秒 |
| benchmark 修正：vz 的空闲内存算上 Apple 的 XPC 进程 | 测量更准确 |

## 结论

**VM 后端（vz、qemu）全面改善：**

| 指标 | vz | qemu |
|---|---|---|
| 端到端启动（热） | 504 → 264 ms（−48%） | 782 → 529 ms（−32%） |
| 切换 | 1237 → 662 ms（−46%） | 1680 → 1060 ms（−37%） |
| 首次启动 | 1151 → 816 ms（−29%） | 1275 → 723 ms（−43%） |
| 冷启动 | 11.5 → 9.1 s（−20%） | — |

guest 内的 `runc create`、`runc start`、就绪等待这些步骤本身并没有改，却也普遍快了 30–50%。所以 vz 和 qemu 的改善里，**有一部分来自 macOS runner 这次更快**，不能全算在这一步的改动上。

**native 和 kvm 在 CI 上看起来变差了，但主要是 runner 的噪声：**

- native 上 guest 内的 `runc create`（23.5 → 58 ms）、`runc start`、就绪等待都慢了 1.5–2.5 倍，而这一步根本没动这几段代码。说明这次分到的 Ubuntu runner 更慢。
- 为了排除噪声，在**同一台本地机器**（8 核 EPYC）上对比 native 的第 0 步和第 1 步：

| 指标 | 第 0 步 | 第 1 步 | 变化 |
|---|---|---|---|
| 首次启动该组合 | 132 ms | 109 ms | 🟢 −17% |
| 同时启动 10 个容器：单个延迟 p50 | 241 ms | 151 ms | 🟢 −38%（吞吐 23 → 55 个/s） |
| 切换（overlap） | 109 ms | 122 ms | ≈（噪声范围内） |
| 切换（overlap + prepare） | — | 72 ms | 新增，比不用 prepare 快约 40% |
| 端到端启动（热） | 53.7 ms | 61.7 ms | 🔺 +15% |

- 热启动变慢 8 ms，原因已经查清：`run` 会先调用 `warm`，而这一步让 `warm` 每次都多做一次预组合 RPC，随后 `run` 自己又组合一遍。这在下一步已修复：只有 `oar warm` 命令做预组合。
- 并发启动在 4 vCPU 的 CI runner 上，单个延迟反而变大（native 305 → 543 ms），但 kvm 的总完成时间是改善的（596 → 557 ms）。原因是现在真的并行执行 runc 了，CPU 少的时候每个请求都会变慢。这种场景下，看吞吐和总完成时间更合适。

**prepare 的效果**（CI 数据，切换耗时，CLI 端到端）：

| 后端 | 不用 prepare | 用 prepare |
|---|---|---|
| native | 197 ms | 145 ms |
| kvm | 129 ms | **89 ms** |
| vz | 662 ms | 561 ms |
| qemu | 1060 ms | 760 ms |

**PR #1（内嵌 iets 求值器）：** 全量构建中的 Nix 求值，native 从 52 s 降到 7.6 s，kvm 从 50 s 降到 7.0 s，不再需要 docker。

## 发现的新问题（第 2 步处理）

1. **vz/qemu 的控制通道往返仍然要 27–42 ms**，kvm 是 6 ms。本地复现后定位到两个原因：
   - **agent 每次 `info` 都会执行一遍 `runc --version`**：在慢 guest 里创建进程要几十毫秒，而每条 CLI 命令一开始都会调用 info；
   - 每个请求都要新建一条到 guest 的连接。

   本地在纯软件模拟的 QEMU 上验证：缓存 runc 版本后，往返从 48 ms 降到 12 ms；再加上连接池，降到 5.4 ms。
2. **CI runner 的噪声会掩盖真实变化。** 下一步起，benchmark 增加「0. 环境基准」一组（宿主机 fork+exec、单核 CPU、磁盘写），用来判断两次数字的差别是不是 runner 造成的。
3. **page cache 共享仍然没测成**：首次读取就没测到缓存增长。需要改用 guest 内 `drop_caches` 之后再测，留到后面处理。
