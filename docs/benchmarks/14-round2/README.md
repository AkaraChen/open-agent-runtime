# Benchmark 第 14 步：第二轮优化（测量修正、启动路径、VM 启动、内核裁剪、view 复用）

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`（CI run 39903653048，commit `f26a053`，分支 `perf2/integrate`）。括号里的变化是相对[第 13 步](../13-baseline/README.md)。**这一次 kvm 和 qemu 的 runner 与基线差异很大**：kvm 基线在 Xeon 6973P-C 上，这次在 EPYC 7763 上（新加的元数据校准：EPYC 慢约 2 倍，这是 6-runtime 与 warm 在 kvm 上"变差"的原因）；qemu 这次的 runner 明显偏慢（fork 1.8 倍、磁盘 0.39 倍）。CPU 型号不同的后端，报告不打 🟢/🔺，只标"CPU 不同"。**每项改动是否采用，以下面的同机交替 A/B 为准**。

## 这一步做了什么

计划见 [`docs/research/perf-round-2-plan.zh-CN.md`](../../research/perf-round-2-plan.zh-CN.md)（issue #8）。先修测量，再逐项做同机 A/B（bench 工作流 `base` 模式，native/kvm 3 轮，vz/qemu 2 轮；判定用新的 `bench compare`）。

### 测量修正

| 改动 | 发现 |
|---|---|
| CLI 等 supervisor 的 100 ms 轮询改为自适应 | 历史上所有 VM 冷启动数字都是 100 ms 的整数倍加 8–16 ms；native 真实冷启动约 20 ms |
| 就绪轮询每轮 exec 一次 `runc state` 再 sleep 10 ms | 就绪时间被量化成 14.6 ms 的台阶 |
| `build.fresh`：机器首次构建单独测 | 基线"求值 6.4 s"几乎全是首次拉 nixpkgs 源码树，求值本身 0.2–0.3 s |
| 组件 build 命令与导入分开计时 | 基线"组件 4 s"是 bench 自己的 `go build`，不在关键路径上 |
| 报告按 CPU 型号判定、元数据校准 | 基线里 native "比 kvm 慢 2–3 倍"是 runner CPU 型号不同 |
| runc 子进程数、agent 侧 CPU 时间、`oar vm profile` | 启动路径的成本可以按次数和 CPU 时间看，不受 runner 噪声影响 |

### 采用的优化（同机 A/B，kvm / native）

| 分支 | 做法 | 同机 A/B 结果 |
|---|---|---|
| `perf2/start-path` | 容器状态读 runc 的 `state.json`；就绪轮询 1 ms 起步、不再 exec；停止经 pidfd 发信号和等待 | runc 子进程：启动 3 → 2，切换 7–8 → 2，预创建切换 → 1。热启动 58.8 → 50.0 / 34.2 → 30.1 ms；replace 切换 119 → 79 / 73 → 49 ms；预创建切换 95 → 49 / 58.5 → 30.4 ms；StopOld 15 → 1.5 / 8.1 → 1.0 ms |
| `perf2/boot-path` | CLI 自适应轮询；`info` 不等 `runc --version`；探测间隔 2 ms | VM 冷启动 409 → 325 / 116 → 20 ms |
| `perf2/extract-buffers` | 每次解包复用一个 128 KiB 缓冲、原始 fd、futimens | kvm 冷 warm 2.30 → 2.16 s；分配 582 → 37 MB |
| `perf2/nix-source` | nixpkgs 源码流水线解包（klauspost gzip、并行写）；nix 阶段不再等基础镜像 digest | 源码缓存热的冷构建 1.72 → 1.49 s；本机首次拉取 4.5 → 1.7 s |
| `perf2/knob-kernel` | 裁剪 guest 内核（DEBUG_*、jitterentropy、SELinux/audit、无关驱动）；`swiotlb=noforce`、`pci=noearly` | kvm VM 冷启动 364 → 234 ms，内核启动 180 → 78 ms，空闲宿主机内存 362 → 274 MiB；qemu 冷启动 2.48 → 1.25 s |
| `perf2/knob-rcu` | guest 内核 `rcupdate.rcu_expedited=1`（`runc create` 里写 `cgroup.procs` 要等一个 RCU 宽限期，见 [runc create 剖析](../../research/runc-create-profile.md)） | kvm `runc create` 24.4 → 20.0 ms，热启动 −7%，快照恢复 −23%；代价：10 个并发启动 +9% |
| `perf2/view-reuse3` | 新闭包的 view 从"已启动且当前空闲"的旧 view 搬走 store path，从没启动过的 view 不拆 | 相邻闭包 reload 的建 view：kvm 285 → 9 ms，native 207 → 6 ms，vz 2.4 s → 41 ms，qemu 3.7 s → 79 ms；direct.reload 374 → 70 / 257 → 41 ms；`first.settled` 不退化（61 → 56 / 33 → 31 ms） |
| `fix/copy-file-range-offset` | native 原地解包的 `copy_file_range` 偏移被推进两次 | bug：短拷贝时写错内容（CPU 采样时必现） |

### 没有采用

| 分支 | 原因 |
|---|---|
| `perf2/view-build`（链接期间不 syncfs、大路径优先） | kvm 上冷 warm 持平，结尾刷盘 28 → 66 ms、增量 warm 352 → 377 ms，三轮都更差 |
| `perf2/knob-fdm`（cgroup2 `favordynmods`） | 与 `rcu_expedited` 消除同一个等待；`runc create` 子项 −10%，端到端持平 |
| vz 宿主机访问改走控制通道 | 延迟持平，吞吐 27 → 20–25 MiB/s |
| crun 替代 runc | 剖析显示 create 5 ms vs 25 ms，值得做；但 CRIU 注解、设备白名单、错误文本三处要改，留作下一轮 |
