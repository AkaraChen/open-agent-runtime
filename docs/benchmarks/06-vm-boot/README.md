# Benchmark 第 6 步：VM 冷启动

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`；括号里的变化是相对[第 5 步](../05-store-views/README.md)。新增的指标没有括号。

## 这一步做了什么

目标是 VM 冷启动。先加测量，再按测量结果改。

| 改动 | 说明 |
|---|---|
| **启动阶段拆分（新指标）** | guest 用 `CLOCK_BOOTTIME` 记录内核交给 init 的时刻（`boot.kernel`）和 switch_root 耗时；宿主机在启动期间读取串口输出，记录看到 init 启动（`boot.toinit`）和 agent 开始监听的时刻，由此得出探测延迟（`boot.detect`）。另加了 `boot-profile` 工作流：在 KVM 上用 `initcall_debug` 启动 guest，列出最慢的内核初始化函数 |
| **amd64 改用 microvm 机型** | 测量显示，q35 机型的 PCI 和 ACPI 枚举（`pci_subsys_init` 183 ms、`acpi_init` 107 ms）占了内核启动的大头。microvm 没有 PCI 总线，只有最小的 ACPI，设备走 virtio-mmio，固件是 qboot（Firecracker 的路子）。`OAR_QEMU_MACHINE=q35` 可以切回 |
| **内核和 initramfs 改用 LZ4** | 解压比 gzip 快约 5 倍。guest 镜像文件名变为 `initramfs.cpio.lz4`，旧的 gzip 镜像仍能启动 |
| **switch_root 不再复制 initramfs** | 改为把 initramfs bind 挂载到自身再切换过去。pivot_root 只要求根有父挂载，所以不必复制 |
| **格式化数据盘更快** | `mkfs.ext4` 不做 discard（稀疏镜像没什么可丢弃，经 virtio 做 discard 比 mkfs 其余部分还慢），也不为在线扩容预留块 |
| **去掉固定等待** | qemu 启动后不再固定等 300 ms；探测 agent 的单次超时从 750 ms 降到 200 ms |
| **修复** | 缩短探测超时后，暴露出一个已有的 bug：vsock 拨号失败时，清理逻辑会对一个带类型的 nil 连接调用 `Close`，导致 supervisor 崩溃。kvm 的 CI 抓到了它 |

## 结论

**1. kvm：重启从 711 ms 降到 308 ms，内核启动从约 440 ms 降到 132 ms。**

| 阶段（kvm） | 第 5 步 | 第 6 步 |
|---|---|---|
| 重启（数据盘已存在） | 711 ms | **308 ms** |
| 冷启动（含首次格式化数据盘） | 810 ms | 708 ms |
| 　宿主机看到 init 启动 | — | 224 ms |
| 　guest 内核启动 | 约 440 ms（第 6 步中途测得） | **132 ms** |
| 　格式化数据盘 | 90 ms | 379 ms（runner 磁盘差异，历次在 90–380 ms 之间） |
| 　agent 开始监听到宿主机连上 | — | 13 ms |

`boot-profile` 工作流在 KVM 上前后对比：q35 时 agent 在 700 ms 可达，microvm 时 **324 ms**；`acpi_init` 从 107 ms 降到 9 ms，`pci_subsys_init` 消失。开发机上用 TCG 模拟时，冷启动从 4.4 s 降到约 2.7 s。

**2. vz 和 qemu（macOS runner）的启动瓶颈不在 guest 内。**

- vz：宿主机 11.8 s 才看到 init 启动，而 guest 自己的时钟显示内核只用了 3.9 s，也就是说**约 8 s 花在 guest 时钟开始之前**（VZ 建虚拟机、加载并解压内核）。LZ4 没有改善这一段。CI 的 Intel Mac runner 本身是虚拟机，VZ 跑在嵌套虚拟化里，这个数字不代表真机（Apple Silicon 上 VZ 通常 1 s 内启动），但仍值得以后调查。
- qemu（arm64，TCG 模拟）：**探测延迟 699 ms**。macOS 上没有 vsock，走 TCP 端口转发：agent 监听之前，转发连接会一直挂住，只能等单次超时。这是下一步要改的：让 guest 在就绪时主动通知宿主机，而不是宿主机轮询。

**3. ⚠️ 两个遗留问题，下一步处理。**

- **kvm 首次启动的 `runc create` 慢**（这次 763 ms，第 5 步 167 ms，第 3–4 步约 1.1 s）。首次启动紧跟在写入了 636 MB 的 warm 之后。我的判断：ext4 默认的 `data=ordered` 模式下，日志提交要先把这些脏数据刷盘，期间创建 overlay 目录之类的元数据操作都要等。修复方向是 warm 结束前就把数据刷盘。
- **vz 运行时开销在第 5 步之后变差。** 按环境基准的 CPU 分数归一化后，readtree、compileall、node 和 python 启动比第 4 步慢 1.5–2.4 倍；kvm 归一化后持平。新指标显示运行时开始时没有待写回的数据，所以第 5 步报告里「后台写回」的猜测**不成立**。vz runner 之间差异很大（fork 延迟 3.5 → 7.9 ms），需要在同一台 runner 上做 A/B 对比才能下结论，下一步做。

## 测量与环境说明

- native 和 kvm 的 `fs.write256m` 都翻了一倍（native 945 → 1915 ms），而 native 这次没有任何改动，属于 runner 磁盘写入速度的差异；增量预热（native 354 → 815 ms）也受此影响。
- native 这次有了快照数据（CI 改为从 PPA 安装 CRIU）：从快照恢复 35 ms，打快照 229 ms。
