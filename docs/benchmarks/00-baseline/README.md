# Benchmark 第 0 步：基线

> 本报告由 `hack/bench` 自动生成（`go run ./hack/bench run` 采集，`report` 渲染），原始数据见同目录的 `results-*.json`。
> 运行环境是 GitHub Actions：native 和 kvm 在 Ubuntu runner（4 vCPU）上；vz 在 macOS 15 Intel runner 上（嵌套虚拟化，整体偏慢）；qemu 在 macOS 15 Apple Silicon runner 上，用的是 **TCG 纯软件模拟**（runner 不支持嵌套虚拟化），CPU 相关数字不代表真实 Apple Silicon 硬件。

## 这是什么

这是优化工作的**第 0 步：基线**。后续每一步都用同一套 benchmark 重跑，报告里的括号会标出相对上一步的变化。

| 步骤 | 内容 | 主要瞄准的指标 |
|---|---|---|
| 0 | 测量工具 + 基线（本报告） | — |
| 1 | 按容器名加锁（并发启动）、预热时预先组合、`prepare` 预创建、修正启动探测 | 并发启动、首次启动、切换耗时、VM 冷启动 |
| 2 | 控制通道复用；VZ 磁盘同步模式 | VM 后端 RTT 与端到端启动、macOS 磁盘 IO 与预热 |
| 3 | EROFS 只读产物 | 预热耗时、guest 缓存、首次挂载 |
| 4 | 应用级快照 | 慢启动应用的切换 |
| 5 | 端口转发 | 宿主机 → 容器 |
| 6 | Cloud Hypervisor 后端 | Linux VM 冷启动 |

## 基线结论

**做得好的地方：**

- **正确性全绿。** 4 个后端上，确定性、闭包隔离、防篡改、连续切换 30 次无泄漏都通过。
- **验收标准达标。** warm compose 端到端：native/kvm 约 13 ms，vz/qemu 约 110 ms，都远低于 1 秒。
- **Linux 上的热路径已经很快。**

  | 指标 | native | kvm |
  |---|---|---|
  | 端到端启动（热，p50） | 55 ms | 67 ms |
  | 切换（p50） | 130–200 ms | 125 ms |
  | overlap 策略的切换失败请求 | 0 | 0 |

- **构建和分发的增量性很好。** 删除一个组件后重建 85 ms；新增 jq 只需下载闭包的 0.21%（1.1 MiB）；增量预热 14–22 ms。

**需要优化的地方（按影响排序）：**

1. **VM 后端的控制通道慢。** vz 和 qemu 的单次 RPC 往返约 50 ms，而 kvm 是 5 ms。每条 CLI 命令会发好几个 RPC，所以 vz 的热启动端到端要 504 ms，而 guest 内只用了 307 ms。（第 2 步）
2. **VM 冷启动里大量时间花在 guest 之外。** vz 冷启动 11.5 s，其中 guest 内核到 agent 就绪只占 4.6 s，6.9 s 在 guest 外；qemu 是 2.0 s / 3.8 s，kvm 是 0.47 s / 1.0 s。初步判断是启动探测的问题：每次连接 agent 失败要等满 3 秒超时才重试。（第 1 步）
3. **macOS 上磁盘 IO 极慢。**

   | 操作 | vz | kvm |
   |---|---|---|
   | 顺序写 256 MiB + fsync | 14.3 s | 1.2 s |
   | 创建 5000 个小文件 | 8.9 s | 0.37 s |
   | 冷预热吞吐 | 12.5 MiB/s | 274 MiB/s |

   预热要把 2.5 万个小文件解包到 guest 磁盘，正好踩中这个弱点。可疑的原因有两个：VZ 磁盘镜像默认的同步模式，以及小文件写入本身。（第 2、3 步）
4. **并发启动被串行化。** 同时启动 10 个容器，单个延迟 p50 是 305 ms（native），单独启动只要 55 ms，吞吐只有 20 个/秒。原因是 agent 用一把全局锁串行处理所有生命周期操作。（第 1 步）
5. **某个组合第一次启动更慢。** native 首次启动 163 ms，热启动 55 ms；vz 是 1151 ms 对 504 ms。原因是第一次要生成模板、建 store 视图，加上缓存是冷的。（第 1 步）
6. **慢启动应用的切换受应用初始化时间限制。** 初始化 3 秒的应用，切换就要 3.1–4.3 s。（第 4 步）
7. **replace 策略在慢环境下失败率很高。** vz 和 qemu 的失败率达到 34–40%，因为停机窗口里包含了新进程的启动时间。overlap + SO_REUSEPORT 只失败 0–2 个请求，是推荐做法。

**测量上的已知问题（第 1 步修正）：**

- **vz 空闲内存偏低。** 19.6 MiB 没有算上 Apple 的 `com.apple.Virtualization.VirtualMachine` XPC 进程（VM 实际运行在那里），所以偏低。
- **page cache 共享没测成。** 读取的文件已经在缓存里，没测到缓存增长，需要换一种测法。
- **全量构建里的 Nix 求值耗时含义不同。** native 和 kvm 是在 docker 容器里求值，每次都要从头下载并解压 nixpkgs，约 50 s；macOS 上 nix 已经装在本机，约 19–34 s。这个数字反映的是构建机的环境，不是 oar 本身的性能。
