# Benchmark 第 7 步：warm 刷盘、qemu 网络与就绪通知、store 视图 A/B

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`；括号里的变化是相对[第 6 步](../06-vm-boot/README.md)。新增的指标没有括号。

## 这一步做了什么

处理第 6 步留下的问题。

| 改动 | 说明 |
|---|---|
| **warm 结束前把数据刷盘**（VM guest） | warm 最后一步（预组合）对 guest 的缓存盘做 `syncfs`。新指标「首次启动前待写回的数据」验证了第 6 步的判断：以前首次启动时还有上 GB 数据没写回，ext4 `data=ordered` 模式下，创建 overlay 目录要等日志提交把它们刷完 |
| **amd64 只在 KVM 下用 microvm** | 第 6 步的 microvm 没有 HPET 和 ACPI PM 定时器，内核只能靠 kvm-clock 得到 TSC 频率。开发机上用 TCG 模拟、宿主机又忙时，PIT 校准会失败，启动卡住（复现过）。没有 KVM 时退回 q35 |
| **qemu 的 guest 网络改为静态配置** | QEMU 用户态网络的地址总是 10.0.2.15/10.0.2.2/10.0.2.3，init 直接配置，不再跑 udhcpc |
| **guest 就绪时主动通知宿主机**（TCP 通道） | agent 开始监听后连回宿主机；宿主机随即取消挂在端口转发里的探测，并给下一次探测足够的时间。agent 启动时就预先取 runc 版本，不让第一次探测去等 |
| **store 视图的 A/B 开关** | `OAR_STORE_VIEW=binds`：每个 store path 一个 bind 挂载（由 runc 在容器自己的命名空间里做），不建硬链接树。benchmark 工作流加了 `ab_store_view` 输入，在同一台 runner 上先后跑两种方案 |

## 结论

**1. kvm 首次启动从 784 ms 降到 40 ms，和后续启动一样快。**

首次启动前待写回的数据，kvm/vz/qemu 上都是 0。代价是 warm 本身变长：kvm 冷 warm 从 2.1 s 到 5.4 s，多出的是把 636 MB 真正写到盘上的时间。以前这部分没有消失，而是记在了首次启动头上。

native 后端没有做刷盘（那会刷整个宿主机文件系统），首次启动前仍有约 1.4 GB 待写回，首次启动 249 ms（后续 31 ms）。这是剩下的问题。

**2. qemu（macOS）探测延迟从 699 ms 降到 230 ms。** 这台 runner 整体慢了约 50%（compileall +54%），所以冷启动总时间没有体现出改善；vz 和 kvm 走 vsock，探测延迟分别是 133 ms 和 1.5 ms。

**3. store 视图：硬链接树（默认）与每路径 bind 的同机 A/B。**

| 指标（同一台 runner，links → binds） | native | kvm | qemu | vz |
|---|---|---|---|---|
| 增量 warm（新闭包） | 613 → **13 ms** | 505 → **89 ms** | 6.6 → **0.4 s** | 3.1 → **0.25 s** |
| `runc create` | **15** → 28 ms | **32** → 90 ms | **409** → 1208 ms | **176** → 378 ms |
| 并发启动 | **125** → 152 ms | **311** → 709 ms | **5.0** → 11.0 s | **3.1** → 5.0 s |
| overlap 切换 | **53** → 69 ms | **117** → 189 ms | **1.7** → 2.6 s | 793 → ❌ |
| 从快照恢复 | **34** → 84 ms | **58** → 104 ms | — | 327 → ❌ |
| readtree（运行时） | 64 → 63 ms | 131 → 127 ms | 2373 → 1640 ms | 3193 → 1673 ms |

结论：**保留硬链接树作为默认**。它在启动、切换和快照上快 1.3–3 倍，这些都在热路径上；bind 方案只在 warm 时省掉建视图的时间（一个闭包一次）。bind 方案在 vz 上还出了故障（切换阶段 agent 连接中断，后续操作卡住）。

macOS runner 上 bind 方案的运行时读取看起来更快，但这个比较**有顺序偏差**：B 方案总是第二个跑，与视图无关的 `fs.write256m` 在 vz 上也快了 2.4 倍（23.7 → 9.8 s），qemu 上快了 22%。再看这一步的常规数据：vz 上视图方案没变，python 启动从 2256 ms 降到 964 ms，readtree 从 4211 ms 降到 2039 ms，按 CPU 分数归一化后回到了第 4 步的水平。所以第 5、6 步报告里 vz 的运行时「回归」，主要是 runner 之间的差异，而不是硬链接树造成的。
