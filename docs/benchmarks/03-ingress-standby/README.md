# Benchmark 第 3 步：入口代理与热备

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`；括号里的变化是相对[第 2 步](../02-control-channel/README.md)。新增的指标没有括号。

## 这一步做了什么

| 改动 | 说明 |
|---|---|
| **入口代理**（`process.ports`） | 每个实例分到一个私有端口，通过环境变量（如 `PORT`）告诉进程；agent 在公开端口上监听并转发。切换时原子地改变转发目标：新连接立刻去新实例，旧实例的在途连接排空后才停掉它 |
| **热备**（`oar prepare --start`） | 新版本提前启动、通过就绪检查，但入口还不把流量给它；切换时只改转发目标 |
| **宿主机访问** | VM 后端由 supervisor 自动把宿主机 `127.0.0.1:<公开端口>` 经控制通道转进 guest；native 后端的入口直接监听在宿主机上 |
| **修复：产物按内容寻址** | benchmark 发现：组件产物以前按「名字」存放，同名但内容不同的组件（不同配置或不同版本）会互相覆盖，导致旧组合无法预热。现在组件按内容哈希存放，基础镜像按锁定的 digest 分目录 |

为什么不给每个容器独立网络命名空间：那需要 veth、网桥和 NAT，在 native 后端上还要改动宿主机网络。「私有端口 + 入口代理」不改动宿主机网络，就达到了同样的目标：无冲突切换、热备、宿主机访问。代价是应用需要能从环境变量读取监听端口。

## 结论

**1. 切换零失败，而且不再依赖 SO_REUSEPORT。**

| 后端 | 入口代理切换：失败请求 | 对比：overlap + SO_REUSEPORT | 对比：replace |
|---|---|---|---|
| native | **0** / 976 | 0 | 74（6.9%） |
| kvm | **0** / 960 | 1 | 60（6.2%） |
| vz | **0** / 463 | 4 | 212（27.7%） |
| qemu | **0** / 662 | 1 | 349（39.3%） |

入口代理切换时，旧实例排空在途连接的 p50 是 0–13 ms。

**2. 慢启动应用：切换从秒级降到毫秒级（热备）。**

| 后端 | 不用热备 | 热备 | 热备准备（提前进行） |
|---|---|---|---|
| native | 3112 ms | **30 ms** | 3.1 s |
| kvm | 3116 ms | **33 ms** | 3.1 s |
| vz | 3414 ms | **174 ms** | 3.4 s |
| qemu | 4917 ms | **428 ms** | 4.8 s |

切换耗时与应用初始化时间脱钩了，只需提前一步执行 `prepare --start`。

**3. 宿主机 → 容器服务（新指标）。**

| 后端 | 请求延迟（每次新建连接） | 下载吞吐 |
|---|---|---|
| native | 0.6 ms | 1.3 GB/s |
| kvm | 1.3 ms | 779 MB/s |
| vz | 19 ms | 42 MB/s |
| qemu | 28 ms | 19 MB/s |

VM 后端的转发要经过控制通道，每个连接都多一次 guest 内的建连。vz 和 qemu 慢主要是 runner 本身慢（环境基准显示 vz 单核比 native 慢 4.5 倍），但这条路径在 macOS 上仍有优化空间，比如直接利用 VZ 的 vsock 转发，而不是逐连接走 RPC。

**4. VM 冷启动拆分（新指标）。**

| 阶段 | kvm | vz | qemu |
|---|---|---|---|
| CLI 拉起 supervisor 进程 | 57 ms | 139 ms | 122 ms |
| 后端创建并启动虚拟机 | 304 ms | 559 ms | 313 ms |
| 虚拟机启动后到 agent 首次可达 | 848 ms | **11.1 s** | 4.8 s |

vz 上 guest 内的 uptime 显示 agent 4.6 s 时已经就绪，比宿主机感知到的晚了约 6.5 s。差距发生在 guest 内核开始计时之前，也就是**内核加载和解压**阶段（x86 的 bzImage 要在 guest 里解压，嵌套虚拟化或 TCG 下很慢）。这是第 5 步的目标：用不压缩或 LZ4 压缩的内核，并精简内核配置。

**5. page cache 共享**这次第一次测出了数字，但第二个容器读取时的增长约为第一个的 70%。这个数字**不可信**：第二个容器自己启动时会运行 node、python、git，也会读文件，增长被算了进去。已经改为容器启动之后再采样，下一份报告修正。

## 测量与环境说明

- **vz 的切换阶段中途失败了一次。** 前一个场景的 `stop --rm` 在慢 runner 上没有完成，后续 `run` 报 "already running"，所以 vz 少了回滚、连续切换等几项。已经改为删除后核验，失败就强制删除。
- **qemu 这次整体偏慢**（热启动 +110%），环境基准显示单核 CPU 慢了 66%，属于 runner 噪声。
