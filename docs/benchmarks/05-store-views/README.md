# Benchmark 第 5 步：store 视图改为硬链接树（issue #2）

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`；括号里的变化是相对[第 4 步](../04-snapshots/README.md)。新增的指标没有括号。

## 这一步做了什么

处理 [issue #2](https://github.com/AkaraChen/open-agent-runtime/issues/2) 的根因：第 3 步之后首次启动变慢。根因是每个 bundle 的 `/nix/store` 视图由「一个骨架目录 + 每个 store path 一个只读 bind」组成，这些挂载常驻在 agent 的挂载命名空间里。`runc create` 新建挂载命名空间时会**复制 agent 命名空间里的全部挂载**，所以常驻的挂载越多，每个容器的创建就越慢；视图被 LRU 淘汰后，首次启动还要重建视图。

| 改动 | 说明 |
|---|---|
| **视图改为硬链接树** | 每个闭包的视图是一棵普通目录树，每个文件都硬链接到共享 store 里的同一个 inode。容器通过**一个**只读 bind 看到它。agent 命名空间里不再常驻任何视图挂载 |
| **按闭包缓存视图** | 视图以闭包（store path 名的集合）为键，只在组件、环境变量或进程配置上不同的 bundle 共用一个视图 |
| **warm 时建视图，并行** | 建视图的成本是每个目录一次 mkdir、每个文件一次 link，在 warm 阶段完成（不在启动路径上），按 store path 并行 |

开发机上对比过的另外两种方案：

| 方案 | 首次启动 | 运行时读取（readtree） | 结论 |
|---|---|---|---|
| 第 4 步：骨架 + 每个 path 一个 bind | 213 ms | 79 ms | 挂载常驻，拖慢所有 `runc create` |
| 只读 overlay 视图（短别名 + 分组） | 81 ms | 102 ms | 多一层 overlay，读取变慢；mountinfo 过长时 CRIU 无法解析，需要分组 |
| **硬链接树（采用）** | **50 ms** | **78 ms** | 读取直接落到底层文件系统，page cache 在 bundle 之间共享 |

## 结论

**1. issue #2 的根因解决：每个容器的挂载从约 140 个降到约 20 个，首次启动的长尾消失。**

| 后端 | 首次启动 | 端到端启动 | `runc create` | 多个 bundle 轮流启动 |
|---|---|---|---|---|
| native | 331 → **96 ms** | 96 → **39 ms** | 53 → **18 ms** | 116 → **38 ms** |
| kvm | 1129 → **191 ms** | 44 → 44 ms | 24 → 21 ms | 50 → 47 ms |
| qemu | 1105 → **721 ms** | 596 → **515 ms** | 396 → **297 ms** | 761 → **476 ms** |
| vz | 753 → 1405 ms 🔺 | 297 → 505 ms 🔺 | 151 → 270 ms 🔺 | 388 → 477 ms 🔺 |

native 上切换也快了一倍（overlap 167 → 80 ms，热备 111 → 66 ms，入口代理 169 → 86 ms），并发启动 439 → 172 ms。快照也受益：kvm 上打快照 180 → 37 ms，恢复 56 → 35 ms（CRIU 要处理的挂载少了）。

**2. 代价：warm 时要建视图。** 新闭包第一次 warm 时要为约 2.2 万个文件各建一个硬链接：native 354 ms、kvm 504 ms，qemu 3.9 s，vz 3.7 s（第 4 步是 0.02–0.7 s）。这一步在 warm 阶段，不在启动或切换路径上，而且同一闭包只建一次。

**3. ⚠️ vz 回归，未解决。** vz 上启动、切换和运行时都明显变慢（readtree 1.5 → 3.2 s，node 启动 427 → 1371 ms，compileall 4.6 → 8.2 s），超出了 runner 噪声能解释的范围（环境基准：CPU 慢 20%，磁盘持平）。kvm 和 qemu 上没有这个现象。

初步判断：建一个视图会产生约 21 MB 的脏元数据（2.2 万个 inode 的链接数变化和新目录），这些元数据随后在后台写回。vz 的磁盘对分散的小块写入很慢，写回和后面的测试争抢磁盘。下一份报告加了「运行时开始时待写回的数据」这个指标来验证。如果判断成立，修复方向是在 warm 结束前把写回做完，让它不影响之后的启动和运行。

## 测量与环境说明

- **kvm 的运行时指标**（compileall 1281 → 1854 ms）**是 runner 噪声**：环境基准显示这台 runner 的单核 CPU 慢了 52%，磁盘慢了 5 倍。按 CPU 换算，运行时开销与第 4 步持平。
- native 和 qemu 仍然没有快照数据：CI runner 上没有 `criu` 软件包（已改为从 PPA 安装，从第 6 步起生效），arm64 guest 里也没有 CRIU。
