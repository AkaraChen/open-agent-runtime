# Benchmark 第 8 步：端口转发不走控制通道（P1-3）、native 刷盘

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`；括号里的变化是相对[第 7 步](../07-warm-flush/README.md)。新增的指标没有括号。

## 这一步做了什么

路线图 P1-3（端口转发与网络），外加第 7 步留下的 native 首次启动问题。

| 改动 | 说明 |
|---|---|
| **qemu（TCP 通道，即 macOS）：由 QEMU 自己转发入口端口** | supervisor 通过 QMP 执行 `hostfwd_add`，让 QEMU 直接监听 `127.0.0.1:<端口>` 并转发进 guest，连接不再经过 supervisor、控制通道和 agent。走 vsock 的 kvm 保持原路径：在那里控制通道本身就很快（约 700 MB/s），QEMU 的用户态网络未必更快 |
| **vz：直连 guest 的 NAT 地址** | agent 在 `ingress.list` 里报告 guest 的 IP，supervisor 直接连 `guestIP:端口`，失败时退回控制通道 |
| **native 也在 warm 结束前刷盘** | 刷的是缓存所在的宿主机文件系统；这部分数据内核本来也会在几十秒内写回 |
| **新指标** | `7-density/vm.rss.after`：同时运行一批容器并删除后，VM 进程树在宿主机上的内存 |

`OAR_QEMU_FORWARD=channel` / `OAR_VZ_FORWARD=channel` 可以切回原路径。

## 结论

**1. 宿主机 → 容器服务：vz 延迟减半，吞吐提高 76%；qemu 延迟降低 35%。**

| 后端 | 延迟（第 7 步 → 第 8 步） | 吞吐（第 7 步 → 第 8 步） | 路径 |
|---|---|---|---|
| vz | 33.0 → **17.5 ms** | 20 → **35 MB/s** | 直连 guest 地址 |
| qemu | 15.0 → **9.8 ms** | 19.8 → 18.5 MB/s | QEMU 自己转发 |
| kvm | 1.3 → 1.9 ms | 701 → 438 MB/s | 不变（控制通道，vsock） |
| native | 0.3 → 0.5 ms | 2628 → 1928 MB/s | 不变（直接监听） |

vz 这台 runner 的 CPU 分数快了约 22%，所以改善里有一部分来自 runner。qemu 的吞吐没有变化，瓶颈在 TCG 模拟本身。开发机上同机对比（TCG）：延迟 14–16 → 10–12 ms，吞吐高约 15%。kvm 和 native 的变化来自 runner（两者路径都没变；这次 kvm 和 native 的 compileall 都慢了约 30%）。

**2. native 首次启动从 249 ms 降到 50 ms。** 首次启动前待写回的数据，四个后端都是 0。代价同第 7 步：native 冷 warm 从 3.3 s 变为 5.1 s。

## 测量与环境说明

- qemu 的探测延迟这次是 1037 ms（第 7 步 230 ms），只有一个样本。这一步唯一影响启动的改动是加了 QMP 套接字；开发机上加了 QMP 之后测了 5 次，都在 168–225 ms 之间。所以我判断是 macOS runner 的一次波动，下一步再看一次。
- 这次 CI 排队时间很长，其他分支（`diag-a`、`diag-b`）也在跑 benchmark，占用了 macOS runner。
