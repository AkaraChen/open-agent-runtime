## 这一步做了什么

路线图（[调研报告](../../research/vm-runtime-landscape.zh-CN.md)第 6 节）里剩下的几项，先做测量再决定是否实现。本步没有改动启动、切换或运行时路径，下面的常规 benchmark 用来确认没有回归，并补上第 8 步 qemu 探测延迟的第二个样本。

## 结论

### P1-2：Cloud Hypervisor 作为 Linux 后端 —— 测量后不采用

新增 `hack/chboot`：用 Cloud Hypervisor 启动同一套 guest（内核加了 PVH 入口，直接启动未压缩的 `vmlinux`；通道是 CH 的 hybrid vsock）。`boot-profile` 工作流在同一台 KVM runner 上先后测 QEMU microvm 和 CH（各 6 次，3 次冷启动、3 次重启）。

| 同一台 runner | QEMU microvm（oar kvm 后端） | Cloud Hypervisor v54 |
|---|---|---|
| agent 可达 | 377–457 ms | **301–347 ms** |
| guest init 启动 | 269–316 ms | 254–265 ms |
| VMM 进程 RSS | 330–340 MiB | **243 MiB** |

CH 快约 20%，内存少约 90 MiB。不采用的原因：

- **网络**：CH 和 Firecracker 都没有用户态网络，容器要联网就得用 tap 设备，需要 root 并改动宿主机网络。oar 的 kvm 后端目前以普通用户运行。
- **场景重叠**：需要 root 的 Linux 生产环境里，native 后端（不用 VM，112 ms 起，运行时零虚拟化开销）已经是更好的选择。
- **维护成本**：多一个 VMM 后端，换来约 70 ms 的启动和 90 MiB 的内存。

测量工具保留，以后如果要做「每沙箱一个 microVM」（那时快照和密度更重要），可以直接复用。**决定（2026-10-21，你确认）：不加。**

### P0-1：产物改为只读镜像（EROFS）—— 测量后不采用

同一个 120 个 store path 的闭包（553 MiB，22446 个文件），在开发机 NVMe 上：

| | 写入 | 刷盘 | 合计 |
|---|---|---|---|
| 解包成文件（现在的 warm） | 1.05–1.09 s | 1.28–2.20 s | 2.4–3.3 s |
| 原样写成 120 个镜像文件 | 0.33–0.39 s | 0.19–0.41 s | 0.5–0.8 s |

写盘成本能降到 1/4 左右，但和闭包视图（第 5 步）配合不起来：

- 硬链接视图要求文件在同一个文件系统里，按 store path 挂载的 EROFS 镜像无法链接进视图；
- 改为挂载，就要在 agent 命名空间里常驻上百个 loop/EROFS 挂载，正是 issue #2 的根因；
- 按闭包合并的 EROFS（多设备 / composefs 那种「元数据镜像 + 共享数据」）可行，但挂载参数会超出长度限制，读路径还要多一层 overlay，需要单独设计。

另外，在最慢的后端上镜像也解决不了瓶颈：vz 上 warm 是 11.5 MB/s，与控制通道吞吐（20–35 MB/s）和 guest 磁盘写入（约 25 MB/s）同一量级，镜像同样要写进 guest 磁盘。

**后续实测：一个能配合闭包视图的方案。** 每个 store path 原样存 tar，并用 `mkfs.erofs --tar=i` 生成只含元数据的索引镜像；每个闭包用 erofs-utils 的 rebuild 模式合并出一个元数据镜像（120 个 path 合并耗时 116 ms，3.0 MiB），它把各个 tar 当作额外设备引用。用新挂载 API（`fsconfig` 逐个传 `device`）挂载，120 个设备不到 1 ms；mountinfo 里不列设备，只有 155 字节，CRIU 能解析。抽查 2000 个文件，内容与硬链接视图一致。

| 同一闭包，开发机 | 硬链接视图（现状） | 合并 EROFS | 合并 EROFS + `directio` |
|---|---|---|---|
| 冷缓存读全部文件 | 4472 ms | **898 ms** | 4006 ms |
| 热缓存读全部文件 | 271–289 ms | 241–249 ms | 323 ms |
| 读取后 page cache 增长 | 672 MiB | **1155 MiB**（双份缓存） | 693 MiB |

不加 `directio` 时，数据会在 tar 文件和 EROFS 里各缓存一份，内存翻倍；加了 `directio` 内存正常，但热读取慢约 19%，而且 guest 内核要从 6.12 升级。**决定（2026-10-21，你确认）：不做，保留硬链接视图。** 运行时读取保持最快，代价是新闭包首次 warm 要建视图（kvm 约 0.7 s，vz 约 2.6 s）。

## 测量与环境说明

- **常规指标没有回归。** kvm 各项都在第 8 步的噪声范围内；qemu 的探测延迟是 216 ms（第 8 步的 1037 ms 是偶发）。
- **vz 这台 runner 很慢**：CPU 分数 278，第 8 步是 152，各项指标随之变慢。宿主机访问延迟 32 ms，按 CPU 分数归一化后与第 8 步相当。
- **native 冷 warm 这次 12.1 s**（第 8 步 5.1 s）。第 8 步起，warm 结束时会对宿主机上缓存所在的文件系统做刷盘；在 CI runner 上这是根文件系统，耗时取决于当时宿主机上待写回的数据量。这是 native 刷盘的真实代价：它换来首次启动 48 ms，而不是 250 ms。
- **⚠️ vz 偶发连接中断（未解决）。** 第 7 步 A/B 的 B 轮和第 9 步的第一次运行里，vz 上各出现过一次 `read response: EOF`，之后的操作失败。这次重跑没有复现，第 8 步也没有。benchmark 已改为在阶段失败时保存 VM 的串口日志和 supervisor 日志（`results-<后端>.<阶段>.*.log`），下次出现时可以看到 agent 是否崩溃。
