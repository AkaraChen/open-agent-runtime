# Benchmark 第 4 步：应用快照

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`；括号里的变化是相对[第 3 步](../03-ingress-standby/README.md)。新增的指标没有括号。

## 这一步做了什么

| 改动 | 说明 |
|---|---|
| **应用快照**（`process.snapshot: true`） | bundle 的第一个就绪实例用 CRIU 打快照（`runc checkpoint --leave-running`，连同可写层）；之后启动同一 bundle 的实例直接从快照恢复（`runc restore`），跳过应用初始化。没有 CRIU、端口被占用或恢复失败时，自动退回正常启动 |
| **guest 里的 switch_root** | init 先离开 initramfs 再启动 agent，于是 runc 可以用 `pivot_root`（CRIU 恢复也需要），不必再用 `--no-pivot` |
| **guest 镜像带上 CRIU** | 内核打开 `CHECKPOINT_RESTORE` 等选项；CRIU 只在 Alpine edge/testing 里有 x86_64 包，**arm64 guest 暂时没有 CRIU**，在那里快照会退回正常启动 |
| **快照 bundle 的 stdio 走管道** | CRIU 只能重新接上管道，接不上宿主机文件，所以只有开了快照的 bundle 才经过一个日志中继进程，其它 bundle 仍直接写日志文件（避免多一个进程的开销） |

## 结论

**1. 慢启动应用：从快照恢复，冷启动从 3 秒级降到几十到几百毫秒。**

测试应用启动时要初始化 3 秒。

| 后端 | 正常冷启动 | 从快照冷启动 | 从快照恢复（guest 内） | 打快照（一次性） | 快照大小 |
|---|---|---|---|---|---|
| kvm | ≥3087 ms | **70 ms** | 56 ms | 180 ms | 1.9 MiB |
| vz | ≥3816 ms | **692 ms** | 596 ms | 1635 ms | 1.9 MiB |
| native | — | — | — | — | — |
| qemu（arm64） | — | — | — | — | — |

通过入口代理切换到从快照恢复的新实例，kvm 上耗时 69 ms，vz 上 997 ms，且全部走了恢复路径。热备（第 3 步）要求提前一步准备；快照不需要提前准备，第二次及以后的启动都受益。

native 和 qemu 这一栏没有数字：CI 的 Ubuntu 24.04 runner 没有 `criu` 软件包（之后改为从 CRIU 的 PPA 安装），arm64 guest 里也没有 CRIU。在开发机上实测 native 从快照恢复约 60–120 ms，amd64 的 qemu（TCG 模拟）约 0.5–0.7 s。

**2. 普通启动没有变慢。** kvm 上 `runc create` 从 37.6 ms 降到 23.6 ms（用 pivot_root 代替 `--no-pivot`），端到端启动从 61.5 ms 降到 43.6 ms。native 的变化在噪声范围内（环境基准显示这台 runner 的磁盘慢了约 4 倍）。

**3. 第 3 步留下的问题仍在：** 每个容器约 140 个挂载，首次启动长尾（kvm 首次启动 1.1 s，几乎全在 `runc create`）。这是 [issue #2](https://github.com/AkaraChen/open-agent-runtime/issues/2) 记录的问题，第 5 步解决。

## 测量与环境说明

- **vz 这次整体偏慢**（启动、切换 +20–80%），但 vz 的 runner 之间差异一直很大，下一步需要再看一次才能判断是不是回归。
- 快照的取舍：快照里包含进程内存（可能有密钥），只保存在 guest 的缓存盘上，不随产物分发；恢复出的实例与快照共享随机数状态，需要唯一性的应用应在恢复后重新播种。
