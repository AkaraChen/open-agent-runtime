# Benchmark 第 12 步：warm 加速（刷盘策略、写回重叠、解包、预建视图、压缩）

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`（commit `8168acc`）；括号里的变化是相对[合并 PR #3 后的总结](../11-final/README.md)，两次不在同一台 runner 上。warm 各项改动的结论以下面的**同机 A/B** 为准。

## 这一步做了什么

目标：让 warm（把产物送进 guest）更快，且不拖慢首次启动和运行时。分五步实现，每一步都在同一台 runner 上做 A/B（bench 工作流的 `ab_env` / `a_env` / `base` 模式）后再决定默认值。

| 步骤 | 做法 | 同机 A/B 结果 | 默认 |
|---|---|---|---|
| 1. 去掉 warm 结束时的刷盘 | 去掉 runc 的 O_SYNC pid 文件后，重新评估刷盘是否必要 | native：冷 warm 4.9/4.5 → 1.4/1.2 s，首次启动持平（48.9/38.9 → 43.2/40.0 ms）。**kvm：首次启动 43 → 407/449 ms**（400 MB 未写回时 `runc create` 等 ext4 日志提交），vz 也出现一次 1534 ms | native 不刷，VM 刷 |
| 2. 刷盘与上传重叠 | 第一版逐个文件 `sync_file_range`：更慢（打散了写入）。第二版：上传期间后台循环 `syncfs` | kvm 冷 warm 3.8 → 2.7 s（结尾刷盘 1453 → 21 ms），qemu 49.0 → 36.3 s；vz 36.9 → 43.3 s、native 1.6 → 2.3 s 变慢 | kvm、qemu 开 |
| 3. 解包少系统调用 | `O_EXCL` 创建代替逐个 `lstat`；属主、权限、时间戳在文件描述符上设，属主或权限本来就对时跳过 | 解包 22,443 个文件 0.90–1.26 → 0.81–0.99 s；结果与 GNU tar 逐文件一致（权限、属主、mtime、大小、链接目标） | 开 |
| 4. 上传时就建视图 | CLI 先告诉 agent 闭包（`view.prepare`），已有的 store path 立即链接，新的到一个链一个 | 冷 warm 结尾等视图：native 787 → 323 ms，kvm 266 → 16 ms，vz 1372 → 0.3 ms，qemu 7.2 → 1.4 s | 开 |
| 5. 慢通道压缩 | 宿主机 zstd 压缩（缓存为 `<产物>.zst`），guest 边解压边解包，校验仍针对原始 tar | qemu：14%、34% 更快（两种顺序各一次，压缩比 3.15）；vz：扣除顺序偏差后约慢 25%（guest 解压比通道传输还慢） | 只 qemu（TCP 通道） |

## 测量与环境说明

- macOS runner 上，第二个跑的那一轮普遍更快：与改动无关的 `fs.write256m` 在 vz 上第二轮快 1.5–2.1 倍。所以 vz 的单次 A/B 要用两种顺序抵消；第 5 步的 vz 结论就是这样得出的。
- 本次完整运行中 vz 的 runner 特别慢（CPU 校准 260，平时 150–220），qemu 的磁盘也偏慢（校准 2321），两者的 warm 数字比同机 A/B 差，不代表回归。
- native 首次启动这次是 126 ms，其中 compose 86 ms（通常 1 ms），只有一个样本；同机 A/B 中两轮都是 40–43 ms。
- vz 的增量 warm 在同机 A/B 中慢约 20%，原因未查明。
- 实验期间 vz 上出现过一次 `oar run` 挂起 40 分钟（这轮改动之前的代码）。agent 现在会在请求超过 60 秒时打印所有 goroutine 的调用栈，供下次定位。
