# Benchmark 第 2 步：控制通道

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`；括号里的变化是相对[第 1 步](../01-concurrency-prepare/README.md)。

## 这一步做了什么

| 改动 | 目的 |
|---|---|
| agent 只在启动时获取一次 runc 版本（以前**每次 `info` 都执行一遍 `runc --version`**） | 每条 CLI 命令都会调用 info，在慢 guest 里每次都要多付几十毫秒 |
| supervisor 维护一个到 guest 的**预建连接池**（4 条，30 秒回收） | 请求不再现场建立 vsock 或转发的 TCP 连接 |
| VZ 数据盘改为 cached + fsync 同步模式（默认是 full，即 `F_FULLFSYNC`）；init 增加缓存盘自愈：挂载失败先 `e2fsck`，还不行就重新格式化 | macOS 磁盘 IO |
| 只有 `oar warm` 做预组合，`run`/`reload` 不再多一次 RPC | 修复第 1 步引入的热启动多 8 ms 的问题 |
| benchmark 新增「0. 环境基准」：宿主机 fork+exec、单核 CPU、磁盘写 | 区分 runner 噪声和 oar 自身的变化 |

## 结论

**控制通道往返大幅下降，所有后端都是 −84% 到 −96%：**

| 后端 | 第 1 步 | 第 2 步 |
|---|---|---|
| native | 4.4 ms | **0.16 ms** |
| kvm | 6.2 ms | **0.78 ms** |
| vz | 27.5 ms | **4.5 ms** |
| qemu | 42 ms | **5.8 ms** |

它带来的连锁收益：

- 单条 CLI 命令快了 42–79%（vz 42 → 25 ms，qemu 72 → 15 ms）；
- warm compose 端到端快了 29–52%（vz 56 → 35 ms，qemu 72 → 42 ms）；
- native 的热启动从 128 ms 降到 84 ms，第 1 步引入的回退也随之消失。

**VZ 磁盘同步模式的收益很小**（guest 内顺序写 −11%）。环境基准给出了原因：这台 runner 宿主机磁盘写 442 MiB/s，而 guest 内只有约 29 MiB/s，瓶颈在嵌套虚拟化下 VZ 的虚拟磁盘本身，而不是同步模式。所以要让 macOS 上预热变快，出路是**少往 guest 磁盘写**（见下面第 4 步），而不是换 IO 参数。

**环境基准证明了 runner 差异很大。** vz runner 的单核 CPU 是 165 ms / 64 MiB sha256，native runner 是 33 ms，相差 5 倍；qemu 是 TCG 模拟，每次波动也大。所以：

- vz 和 qemu 上 ±30% 以内的变化，应先看环境基准再下结论；
- 这次 qemu 的切换耗时 +46%，guest 内各阶段也同步变慢，属于 runner 噪声。

**VM 冷启动仍有约 5.5 s（vz）花在 guest 之外。** 这次已经加上 supervisor 的分阶段计时（拉起进程、虚拟机启动、agent 首次可达），下一轮数据会给出拆分。

## 根据数据调整后续计划

原计划的第 3 步是 EROFS。数据显示：对生产环境（Linux）影响最大的，是**切换时的停机、慢启动应用和端口转发**；预热慢主要是 macOS 开发机的问题。所以调整顺序如下。

| 步骤 | 内容 | 主要指标 |
|---|---|---|
| 3 | **由 oar 掌控入口流量**：每个容器独立网络命名空间，agent 内置 TCP 入口代理，宿主机可访问（端口转发）；切换 = 原子地改变代理目标；支持「热备」，即新版本提前启动并就绪，切换时只需转移流量 | 慢启动应用的切换耗时、切换失败请求（不再依赖 SO_REUSEPORT）、宿主机 → 容器 |
| 4 | **零拷贝产物**：用 Go 写 EROFS 生成器，每个 store path 一个只读镜像；VM 通过 virtio-fs 直接挂载宿主机上的镜像，native 直接 loop 挂载，不再解包 | macOS 冷预热（目前 33 s）、guest 缓存占用 |
| 5 | VM 冷启动：依据新的分阶段计时优化，评估 Cloud Hypervisor 后端 | VM 冷启动 |

应用级快照（CRIU）**暂缓**：guest 用的 Alpine 3.22 没有 CRIU 软件包，自己静态编译成本高、维护难。第 3 步的热备能覆盖「已知下一个版本」的切换场景，快照留到需要「冷启动即恢复」时再做。
