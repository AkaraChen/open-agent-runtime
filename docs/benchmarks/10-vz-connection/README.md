# Benchmark 第 10 步：修复 vz 偶发连接中断

> 本报告由 `hack/bench` 自动生成，原始数据见同目录的 `results-*.json`；括号里的变化是相对[第 9 步](../09-evaluations/README.md)。新增的指标没有括号。

## 这一步做了什么

修复 vz 上偶发的连接中断：`read response: EOF`，之后的操作全部失败。第 7 步 A/B、第 9 步、第 10 步第一次运行各出现过一次，约占 vz 运行的 3/10。

| 改动 | 说明 |
|---|---|
| **失败时保存 VM 日志** | benchmark 某个阶段失败时，把 VM 的串口日志和 supervisor 日志存到结果旁边并上传。这次抓到的日志显示：guest 里的 agent 一直正常（没有崩溃或重启），supervisor 也没有任何记录 |
| **宿主机 socket 代理：重试并记录连接失败**（根因） | CLI 经宿主机 socket 访问 agent 时，supervisor 要先连上 guest。以前连接失败会直接、悄悄地关掉 CLI 的连接，CLI 看到的就是 `read response: EOF`。vz 刚启动时，supervisor 同时在为连接池建 4 个连接，这时出现连接失败的可能最大。现在会退避重试约 1.3 s，仍然失败就写日志 |
| **连接池：交出连接前检查是否还活着** | 能对 socket 做非阻塞 peek 时（vsock、TCP）检查对端是否已关闭，不付等待代价。中途版本对拿不到 socket 的连接（vz、native 的进程内 pipe）用 100 µs 超时读来检查，结果让 native 每个请求多了约 0.7 ms，已改为不检查这类连接 |

## 结论

**1. vz 连接中断：修复后连续 3 次运行都没有出现。** 修复前约 3/10 的 vz 运行会失败。3 次还不足以证明问题彻底消失，但失败日志已经能看到原因（连接 guest 失败）；如果再出现，supervisor 日志会记录具体错误。

**2. 没有引入开销。** native 控制通道往返 0.2 ms（第 9 步 0.5 ms）。中途版本曾升到 1.2–1.3 ms，原因见上表最后一行，已修复。kvm 各项与第 9 步持平。

## 测量与环境说明

- vz 的控制通道往返噪声很大：每一步的单次样本都在 3–300 ms 之间。这次 p50 是 14.4 ms（第 9 步 7.2 ms）。这次运行还包含 vz 上的 100 µs 检查；它在报告生成前已经移除（commit b5c4173），以免 macOS 定时器精度带来额外等待。
